사이트를 짜기 전에 **무엇을 실을지** 먼저 정한다. 이 문서가 그 목록이다.
화면 형태(스크롤 페이지 / 슬라이드 덱)는 아직 정하지 않았다 — 내용이 정해진 뒤에 고른다.

### 1-2. 살릴 것 — 이 덱의 강점

1. **문제 → 가설 → 설계 → 결과 → KPI 가 끝까지 닫힌다.**
   두 프로젝트 다 같은 뼈대다. 포트폴리오에서 가장 값나가는 부분이니 이 구조를 유지한다.

2. **가설을 수치로 세웠다.** (05) 「불일치율 · 첨부 누락율 · 전표 리드타임」 세 지표로
   시장 문제를 수치화하고 들어간다. 감이 아니라 근거로 시작한 것이 드러난다.

3. **결과를 매출까지 잇는다.** (13) 운영 지표(자동화율)에서 멈추지 않고
   결제 전환율 · 고객 유지율 · 매출 상승률로 연결한다. PM 포지션에서 이게 핵심이다.

4. **사용자 목소리가 있다.** (17) 고객사 담당자 6명 인용. 숫자 뒤에 사람이 있다는 증거다.

5. **"입력에서 검증으로"** — 07·09·10 에 반복해서 나오는 한 문장이다.
   이 덱의 주제문이다. 웹에서는 이걸 상단에 한 번 크게 박는 게 좋겠다.

인사 발령에 맞는 문장으로 새로 써야 한다. **Figma 도 같이 고치는 게 맞다.**

**구조상 손봐야 할 것**

- **슬라이드 02 의 자기소개가 한 덩어리 1,000자다.** 슬라이드에서는 넘어가지만
  웹에서는 아무도 안 읽는다. 이미 안에 `1. 구조와 논리의 깊이` · `2. 브랜드와 소통의 폭`
  두 축이 있으니, 그 축으로 쪼개고 각 축에 소제목을 준다.
- **수치의 출처가 안 보인다.** 94% · 98% · 89% · 86% 가 어디서 나온 값인지 덱에는 없다.
  웹에서는 각 수치 밑에 근거를 한 줄로 붙인다 (측정 기간 · 모수 · 산식).
  이게 없으면 숫자가 클수록 오히려 의심받는다.
- **프로젝트 2 가 프로젝트 1 에 비해 얇다.** 1 은 10장(04~13), 2 는 4장(14~17)이다.
  웹에서는 분량 차이가 슬라이드보다 더 드러나니, 2 를 보강하거나 1 을 줄여 균형을 맞춘다.

### 1-4. `../404` 저장소와 이어 붙일 것 — 이번에 찾은 것

**"슬라이드로 설명한 것을 실제로 돌아가는 화면으로 만들었다"** 가 되는 구성이다.

## 2. 청담원 — 레퍼런스 정리

### 축: **AI 파이프라인을 구성해서 기획부터 구현까지 했다**

이게 청담원 섹션의 뼈대다. GPRO 와 차별점이 뚜렷하고, 무엇보다 **증거가 남아 있다.**

⚠️ 주의 — "AI 로 빨리 만들었다" 로 쓰면 약해진다. 그건 누구나 말한다.
강한 건 **파이프라인을 설계했고, 그 파이프라인의 실패 모드까지 문서로 남겼다**는 쪽이다.
아래 증거는 전부 후자를 받친다.

- 기획 문서: Confluence 「청담원 프로젝트」(CDW) — **본인 작성 97개** (2026-05-18 ~ 09-01)
- 구현: `~/cheongdamwon-platform` — **261 커밋** (2026-06-22 ~ 09-10) · 테스트 969개 통과
- 저장소 안 PRD 7종 (`docs/specs/*-prd-2026-09-09.md`, 각 1,100~1,400줄)

⚠️ 정본 클론은 `~/cheongdamwon-platform` 이다 (`~/Documents/GitHub/` 쪽 아님 — CLAUDE.md 참고).

### 2-1. 파이프라인 실물 — 단계별로 도구가 붙어 있다

### 2-2. 이 파이프라인이 좋은 이유 — 세 가지

**① 대상을 알고 자동화했다.**
`cdw-weekly-report-draft` 에는 이렇게 적혀 있다 —
*"보고 대상은 개발 지식이 없는 상급자이므로, 개발 용어(PR·브랜치·커밋·toast·DS·schema·
마이그레이션·403/500·embed 등)를 절대 쓰지 말고 «무엇이 좋아졌나» 중심의 쉬운 한국어로"*.
git log 를 요약한 게 아니라 **번역 계층을 자동화**한 것이다. 기획자가 할 법한 자동화다.

**② 자동화의 실패 모드를 문서로 남겼다.**
`capture-help-shots.mjs` 머리말: *"각 컷마다 화면에 있어야 할 문구를 확인한 뒤 찍는다.
(실제로 처음엔 로그인 폼이 접혀 있는 걸 못 보고 로그인 화면만 5장 찍었다)"*
— 조용히 잘못 찍히는 것을 막으려고 컷마다 검증을 넣었다. 같은 파일에 안전장치도 있다:
실데이터가 캡처에 들어가지 않게 로컬 시연 데이터만 쓰고, 공단 인증서 세션을 물고 있는
Chrome 프로필을 건드리지 않으려고 자기 프로필로 띄우고, 임시 계정은 `forceDelete` 한다.

**③ 판단은 사람에게 남겼다 — 말한 대로 만들었다.**
AI 활용법 강의 노트(2026-07-30)에 본인이 적어 둔 원칙:
*"개인정보·계약·법령 관련 업무는 자동화 대상이더라도 최종 확인은 사람으로 남긴다."*
그리고 실제로 케어플랜 매핑이 그렇게 돼 있다 — 자동 확정이 아니라 **초안 제안**이고,
담당자가 켜고 끄고 다듬어 저장해야 기록이 된다(NA-06).
**적어 둔 원칙과 만든 물건이 일치한다.** 이 대조를 포트폴리오에 그대로 보여준다.

### 2-3. 「자동화 5단계」와 대조 — 5단계까지 올라갔다

같은 강의 노트에 자동화 계획의 뼈대 5단계가 있고, *"1번을 건너뛰고 4~5번부터 시작하면
대체로 실패합니다"* 라고 적혀 있다. 실제로 건너뛰지 않았다.

| 단계 | 청담원에서 |
| --- | --- |
| ① 반복작업 표준 매뉴얼 | 매뉴얼 19종 · 도움말 투어 48단계 · `CLAUDE.md` 운영 규칙 |
| ② 외부 시스템 연결 | 공단·희망이음 **API 12종** + MCP (Confluence·Jira·Figma·Playwright·Flow) |
| ③ 팀별 기능 묶음 | 백오피스 **EMR 그리드 표준** — 흩어진 화면을 한 문법으로 |
| ④ 주기 자동 실행 | 예약 에이전트 5종 (매일 09:00 / 평일 17:00 / 금 17:30) |
| ⑤ 에이전트 오케스트레이션 | `team-report-hub-refresh` — 기획·마케팅 산출물을 한 아티팩트로 |

⚠️ 사실관계 — 이 강의는 **본인이 들은 것**이다(대상: 전 직원). 진행한 것이 아니다.
포트폴리오에 "강의했다" 로 쓰면 안 된다. 쓸 수 있는 건 **"들은 로드맵을 실제로 5단계까지
실행했다"** 까지다. 노트 자체도 단순 필기가 아니라 항목별로 재구성하고 본인 해석
("포인트:", "다만 확정본은 내부 규정과 대조 검토가 필요합니다")을 달아 둔 것이라 그대로 근거가 된다.

### 2-6. 강조할 것 — 다섯 갈래

**① 전략 판단으로 시작했다**
「플랫폼 구현 전략 비교 요약」(2026-05-20)이 첫 문서 축에 든다. 5개 축(MVP 속도 ·
데이터 동기화 · 무결성/확장성 · 초기 비용 · 장기 운영 리스크)으로 두 안을 비교하고,
**2안(신규 구축) + 핵심 기능만 먼저**를 건의했다.
비전문가용 비유로 썼다는 점이 좋다 — "법인카드 내역이 1원도 틀리지 않고 꽂혀야 하듯",
"제대로 된 기초 공사". 경영진을 설득하는 문서라는 걸 알고 쓴 글이다.

**② 도메인을 규칙으로 옮겼다 — 케어플랜 자동 초안 매핑**
가장 깊은 기획이다. 「욕구사정 10섹션 → 케어플랜 초안」 매핑을 섹션별 표로 전부 정의했다.

- 척도 단계를 문구로 대응 (`[1]` 지켜보기 / `[2]` 직접 도움 / `[3]` 전적인 도움)
  — 방문요양 법정 예시 단계와 맞춘 것
- 초기상담기록지 매핑과 **같은 엔진의 두 번째 입력**으로 설계하고 병합 규칙을 정함
- 중점 승격 우선순위: 안전(낙상·욕창) → 건강 → 정서·인지
- **법정 제약을 규칙에 박음** — 시행규칙 제14조 금지 3종은 어떤 입력으로도 켜지지 않는다 (NA-04)
- **자동 확정이 아니라 초안 제안** — 담당자가 켜고 끄고 다듬어 저장해야 기록이 된다 (NA-06)

"AI 로 자동 생성" 이 아니라 **규칙으로 옮길 수 있는 것만 옮기고 판단은 사람에게 남긴** 설계다.
이 절제가 오히려 강점이니 그대로 드러낸다.

**③ 공단·희망이음 API 12종 실연동**
근거: `docs/HANDOVER-2026-09-02.md` · `docs/longterm-api-spec.md`

- 공단 장기요양(롱텀) 조회 5종 + 희망이음(SSiS) 조회 3종 · **쓰기 4종**.
  직원 등록 · 자격 등록 · 인력변경(입사/퇴사) 신고까지 **실제 신고 확인**까지 갔다.
- **벤더가 실패를 성공으로 준다** — `Status=OK · ErrorCode=0 · Message=성공` 인데 아무 일도 안 일어난다.
  `Result` 안의 처리 메시지를 봐야 한다는 걸 4번 당하고 알아냈고 `assertAccepted` 로 방어를 박았다.
- **문서가 틀렸다** — 「[암호화]」 안내 문구가 아니라 데모 화면 체크박스가 정본. 실측 대조로 밝혀냄.
- **"등록"과 "신고"는 다른 일** — 미신고면 공단 급여 산정에 안 잡힌다. 화면에 「공단 미신고」 배지를 붙임.
- **0건 응답을 삭제로 읽지 않는 방어** — 벤더 장애로 0행이 오면 센터 전체가 사라진다.
- 응답에 섞여 오는 주민등록번호를 적재 시 제거(`PAYLOAD_DROP`) + `$hidden` 직렬화 제외.

**④ 흩어진 화면을 하나의 문법으로 — 백오피스 EMR 그리드 표준**
상담·수급자·채용·직원 전 화면을 하나의 격자 문법으로 통일했다
(정렬 · 틀고정 · 열 조절 · 인라인 편집). `consult-detail.blade.php` 만 47번 고쳤다.
중간에 셸을 LNB→GNB→LNB 로 두 번 갈아엎은 이력이 있다 — **되돌린 판단도 이야깃거리다.**
디자인 시스템 쪽에서는 라운드 스케일을 실측 기준으로 전역 재정의하고 케어닷 브랜드로 리스킨했다.
*시니어·보호자 친화 UI* 라는 제약이 명시적으로 있던 프로젝트다.

**⑤ 만든 걸 쓰게 만드는 것까지 — 매뉴얼 18종**
「상담 화면 익히기」 · 「전화 상담 등록하기」 · 「보류·이탈로 정리하기」처럼
**업무 동사로 제목을 단** 매뉴얼을 썼다. 기능 이름이 아니라 사용자가 하려는 일로 묶은 것이다.
화면 안 도움말 투어(`docs/tour-copy.md`)도 같이 붙였다.

그 밖: 공개 사이트(서비스 3종 · 정부지원 가이드 3종 · 센터 찾기 · 법적고지 5종) ·

### 2-8. 공개할 때 조심할 것

- 회사 private 저장소·위키다. 코드·문서·디자인을 그대로 옮기지 않는다. **재현물과 요약만 싣는다.**
- 실제 직원 이름·사번(핸드오버 문서에 있다) · 센터명 · 인증서 관련은 전부 뺀다.
- 주민등록번호가 오가는 화면이라 **더미값도 실제 형식으로 두지 않는다**
  (404 에서 쓴 방식대로 자리수만 맞춘 0).
- 고객사·경쟁사 수치는 익명으로. 경쟁사 비교분석·가맹비 시장조사는 **회사 영업 자료**라
  포트폴리오에 수치를 옮기지 않는다 — "경쟁사 분석을 했다" 까지만.
- 케어플랜 매핑표 원문은 회사 자산이다. **방법론(척도→문구 대응, 법정 금지 규칙)만 설명**한다.

## 3. 아직 안 정한 것

   GPRO 는 94%·86% 같은 개선율이 있는데 청담원은 아직 없다. 지금 쓸 수 있는 건
   규모 수치뿐이다(문서 97 · 커밋 261 · 테스트 969 · API 12종 · 매뉴얼 19 · 투어 48단계).
   파이프라인 축이면 **「사람이 안 해도 도는 일」의 개수·주기**가 더 맞는 지표일 수 있다.
4. **Figma 시안을 고칠지** — 1-3 의 오탈자와 슬라이드 14 GOAL 은 웹만 고치면 원본과 갈라진다.
